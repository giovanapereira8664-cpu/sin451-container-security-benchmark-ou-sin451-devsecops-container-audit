Configuração insegura em contêineres: ferramentas clássicas × IA

Desenvolvimento e avaliação empírica de uma ferramenta de análise de vulnerabilidades

Giovana Pereira da Silva, Gabriel Mello Lobo e Lucas Dias de Queiroz · novembro de 2026

O problema

Quase toda aplicação hoje roda em contêiner, e a segurança começa no arquivo que monta esse contêiner.

Um Dockerfile ou docker-compose.yml mal escrito leva a falha para todo ambiente onde a imagem rodar.

Pergunta do trabalho

Para detectar configuração insegura, ferramentas clássicas de análise estática são melhores ou piores que modelos de linguagem? O tamanho do modelo importa?

As 3 falhas analisadas

Versão não fixada

A imagem ou o pacote pode mudar sem você saber?

RUN apk add --no-cache curl
image: redis:latest

Contêiner como root

Se a aplicação for invadida, o atacante já é administrador?

Segredo escrito no arquivo

Quem tem o repositório ou a imagem consegue ler a senha?

Versão não fixada: impacto e mitigação

Impacto

  • Cada build pode puxar uma imagem diferente: o que foi testado não é o que vai para produção.
  • Uma versão nova pode trazer vulnerabilidade conhecida (CVE) ou quebrar a aplicação sem aviso.
  • Se a imagem publicada for adulterada (ataque à cadeia de suprimentos), ela entra sem nenhuma barreira.

Mitigação

  • Usar tag com número de versão e, de preferência, o digest @sha256 da imagem.
  • Fixar a versão dos pacotes do sistema (apt-get install pacote=versão) ou instalar só o necessário.
  • Atualizar de forma controlada, com Dependabot ou Renovate abrindo pedidos de mudança revisados.
  • Varrer as imagens com um scanner de CVE (por exemplo, Trivy) antes de publicar.
Inseguro
FROM python:alpine
RUN apk add --no-cache curl
image: redis:latest
Corrigido
FROM python:3.12-alpine3.20@sha256:<digest>
image: redis:7.4.1-alpine

CIS Docker Benchmark 4.x; Hadolint DL3006/DL3007/DL3008; Checkov CKV_DOCKER_7

Contêiner como root: impacto e mitigação

Impacto

  • Uma falha na aplicação vira controle total do contêiner: instalar ferramentas, ler e alterar qualquer arquivo.
  • Root no contêiner é o mesmo usuário 0 do servidor: uma falha do kernel ou do Docker facilita escapar para o host.
  • Com privileged: true, o contêiner recebe todas as capacidades do Linux e acesso aos dispositivos do host.

▶ No laboratório vulnerável: uid=0(root) gid=0(root) groups=0(root),0(root),1(bin),2(daemon),3(sys),4(adm),6(disk),10(wheel),11(floppy),20(dialout),26(tape),27(video), 41 capacidades do Linux.

Mitigação

  • Criar um usuário sem privilégios e terminar o Dockerfile com USER app.
  • No compose, usar user: e remover privileged: true.
  • Retirar capacidades (cap_drop: [ALL]) e ativar no-new-privileges; usar read_only quando possível.
  • Considerar Docker rootless ou user namespaces no servidor.
Inseguro
USER root          # ou nenhum USER
privileged: true
Corrigido
RUN adduser -D -u 10001 app
USER app
cap_drop: [ALL]
security_opt: ["no-new-privileges:true"]

CIS Docker Benchmark 4.1 e 5.4; Hadolint DL3002; Checkov CKV_DOCKER_3/CKV_DOCKER_8

Segredo escrito no arquivo: impacto e mitigação

Impacto

  • A senha fica no histórico do Git para sempre, mesmo que o arquivo seja corrigido depois.
  • Fica gravada nas camadas da imagem: qualquer um com a imagem lê com docker history ou docker inspect.
  • Com a senha, um atacante acessa o banco ou o serviço direto, sem precisar de outra falha.

▶ No laboratório vulnerável, a senha foi lida da imagem com docker history: ENV DB_PASSWORD=****

Mitigação

  • Passar segredos só na hora de rodar (variável de ambiente externa, arquivo .env fora do Git).
  • Usar secrets do Docker/compose ou de um cofre (Vault, gerenciador da nuvem); no build, BuildKit --secret.
  • Ativar detecção de segredos no repositório (Checkov secrets, gitleaks) antes do commit.
  • Se vazou: trocar a senha imediatamente; apagar do arquivo não basta.
Inseguro
ENV DB_PASSWORD=abc123
MYSQL_ROOT_PASSWORD: senha123
Corrigido
environment:
  DB_PASSWORD: ${DB_PASSWORD:?defina}
# ou secrets: do compose / BuildKit --secret

OWASP Secrets Management Cheat Sheet; CWE-798; Checkov CKV_SECRET_*

Como medimos

  • Acerto (TP): mesmo arquivo, mesma categoria, até 2 linhas de distância do gabarito.
  • Alarme falso (FP): apontou e não era falha. Escape (FN): falha que ninguém apontou.
  • Cada falha do gabarito só pode ser acertada uma vez; repetições não contam como acerto.
  • Intervalo de confiança de 95% por bootstrap (1000 reamostragens dos arquivos).

Precisão = TP ÷ (TP + FP)
do que apontou, quanto era verdade

Recall = TP ÷ (TP + FN)
das falhas reais, quantas achou

F1 = média harmônica das duas

Limitações

  • Corpus pequeno e gabarito anotado por uma só pessoa.
  • Checkov não analisa docker-compose (só o detector de segredos) nem alguns nomes de Dockerfile.
  • Regras próprias não conhecem o usuário padrão da imagem base.
  • Respostas da IA podem variar entre dias; o cache guarda as usadas.
  • Catálogo de modelos da NVIDIA muda com frequência.

Conclusão

  • As regras próprias obtiveram o maior F1 geral no conjunto de teste (0,8387; 0,8000 em todos os arquivos), superando A1 (0,7647) e A0 (0,3404).
  • Entre os modelos de IA no teste, IA-grande alcançou F1 de 0,5965 contra 0,4444 de IA-pequeno e 0,0000 de IA-medio, destacando-se em HARDCODED_SECRET (0,7000 vs. 0,5263).
  • A análise clássica e as regras próprias rodam localmente em segundos (7,7 s no Hadolint, 3,4 s no Checkov e 0,05 s nas regras próprias) sem tokens, enquanto a IA tem maior latência por arquivo (cerca de 6–23 s no IA-grande vs. ~0,7–2,1 s no IA-pequeno) e consome tokens de entrada e saída.
